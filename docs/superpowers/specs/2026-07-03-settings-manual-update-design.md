# 设置页手动更新功能设计

日期：2026-07-03
状态：已确认

## 1. 背景

桌面端目前只有自动更新链路：应用启动或定时检查 GitHub Release，发现正式版后静默下载，下载完成后才在左下角提醒用户安装。

该链路能保证更新触达，但用户无法主动确认当前是否有新版，也无法自行决定何时开始下载。本设计在设置页增加完整的手动更新入口，同时保留现有自动更新兜底。

## 2. 目标

1. 桌面端设置页提供“检查更新”入口。
2. 手动检查发现新版后不自动下载，由用户点击“下载更新”。
3. 下载完成后显示“安装并重启”，点击后继续经过现有确认弹窗。
4. 自动更新与手动更新共用同一状态、下载文件和安装任务。
5. 用户主动操作失败时给出明确反馈；后台自动检查的网络失败继续保持静默。
6. 保持现有稳定版更新、安全校验和安装机制不变。

## 3. 非目标

- 不增加 beta、rc 等预发布更新通道。
- 不增加“自动下载更新”偏好开关。
- 不支持暂停、取消或断点续传。
- 不在应用内渲染完整 Release Markdown。
- 不为浏览器运行模式提供桌面安装能力。
- 不新增数据库字段、第三方依赖或第二套更新控制器。

## 4. 已确认的产品决策

### 4.1 自动与手动入口

- 自动入口保持现状：启动或定时检查，发现新版后静默下载。
- 手动入口采用分步流程：检查更新 → 下载更新 → 安装并重启。
- 两个入口订阅并操作同一个主进程更新控制器。
- 自动下载已经开始时，设置页直接展示该任务的进度，不创建重复下载。

### 4.2 设置页位置

软件更新卡片放在“全局设置”之后、“数据迁移 / 备份”之前。该位置保证业务设置优先，同时让更新能力保持独立且容易找到。

### 4.3 新版本信息

发现新版后展示：

- 当前版本；
- 最新版本；
- Release 标题；
- 发布日期；
- “查看官方发布说明”外链；
- “下载更新”按钮。

完整发布说明由系统浏览器打开 GitHub Release 页面，不在应用内解析或渲染 Markdown。

### 4.4 安装确认

下载完成后显示“安装并重启”。点击后复用现有确认弹窗，用户再次确认才执行安装并关闭、重启应用。

### 4.5 左下角提醒

保留现有左下角更新提醒，但仅在用户需要处理时显示：

- 已下载，等待安装；
- 正在准备或安装；
- 下载、校验或安装失败。

`available` 和 `downloading` 继续由设置页展示，不把侧边栏变成长驻更新入口。

## 5. 架构

### 5.1 唯一事实来源

`desktop/src/update-controller.ts` 继续作为更新状态的唯一事实来源。自动入口、设置页和左下角提醒都读取相同的 `UpdateState`，并通过现有状态广播同步。

不创建前端独立下载状态，不创建第二个主进程控制器，也不复制下载、SHA-256 校验或安装逻辑。

### 5.2 检查模式

控制器内部的检查方法增加明确的下载策略：

- 自动检查：`manual: false`，发现候选版本后允许静默调用 `downloadUpdate()`。
- 手动检查：`manual: true`，绕过后台长退避，但发现候选版本后停在 `available`。

渲染进程暴露的 `checkForUpdates()` 始终代表用户主动检查，因此主进程 IPC handler 固定调用“手动检查、不自动下载”模式。自动启动和定时轮询仍由主进程内部调用自动模式。

### 5.3 共享订阅

提取一个小型 `useDesktopUpdateState` Hook，封装现有的：

- `updates.getState()` 初始读取；
- `updates.onUpdateStateChanged()` 状态订阅；
- `normalizeUpdateState()` 兼容处理。

`DesktopUpdateNotice` 和新的 `DesktopUpdateSettingsCard` 共用该 Hook。不增加全局 Context 或新的状态管理库。

### 5.4 Release 摘要字段

为共享更新状态补充两个可选字段：

- `releaseTitle?: string`
- `publishedAt?: string`

字段由现有 Release 候选数据写入，沿用当前状态持久化和前端 bridge 类型。旧 `state.json` 不含这些字段时保持兼容，界面退化为仅展示版本号和发布说明链接。

## 6. 状态与界面行为

| 状态 | 设置页显示 | 主操作 |
|---|---|---|
| `idle`，尚未检查 | 当前版本 | 检查更新 |
| `idle`，最近检查确认无新版 | 当前已是最新版、当前版本、最近检查时间 | 重新检查 |
| `checking` | 正在连接更新服务 | 禁用按钮 |
| `available` | 当前版本、最新版本、标题、发布日期、发布说明链接 | 下载更新 |
| `downloading` | 目标版本和下载百分比 | 禁用按钮，不提供暂停或取消 |
| `downloaded` | 新版本已准备好、安装影响说明 | 安装并重启 |
| `preparing` / `installing` | 正在准备或安装 | 禁用按钮 |
| `error` | 按错误类型显示原因 | 检查、重新下载或重新安装 |

浏览器运行模式下整张卡片不渲染。

## 7. 数据流

### 7.1 手动检查

1. 用户点击“检查更新”。
2. 设置页检查最近一次 `lastCheckedAt`。
3. 距离上次完成检查不足 60 秒时，直接复用现有状态，不发起新的网络请求。
4. 否则通过 desktop bridge 调用 `checkForUpdates()`。
5. 主进程进入 `checking` 并广播状态。
6. 没有新版时回到 `idle`，设置页显示“当前已是最新版”及检查时间。
7. 有新版时进入 `available`，等待用户点击下载。

### 7.2 手动下载

1. 用户在 `available` 状态点击“下载更新”。
2. 设置页调用现有 `downloadUpdate()`。
3. 主进程继续使用 `.partial` 临时文件、SHA-256 校验和原子重命名。
4. 下载进度通过现有状态广播实时更新。
5. 校验通过后进入 `downloaded`，设置页和左下角提醒同时可见。

### 7.3 手动安装

1. 用户点击“安装并重启”。
2. 前端打开现有安装确认弹窗。
3. 用户确认后调用现有 `installUpdate()`。
4. 主进程准备安装、退出当前应用并重新打开新版本。

### 7.4 自动任务已在执行

设置页不创建独立任务：

- 自动检查中：展示 `checking`。
- 自动下载中：展示共享进度。
- 已下载：直接展示“安装并重启”。
- 准备或安装中：展示进行中状态并禁用操作。

## 8. 并发与限频

### 8.1 单任务约束

控制器在以下状态拒绝相同或冲突的重复操作：

- `checking` 时不再启动第二次检查；
- `downloading` 时不再启动第二次下载或覆盖为新的检查状态；
- `preparing` / `installing` 时不再检查、下载或重复安装。

状态必须在首个异步文件或网络操作之前同步切换，以关闭同一事件循环内的竞态窗口。

### 8.2 手动检查限频

设置页使用已有 `lastCheckedAt` 实现 60 秒短限频：

- 检查进行中按钮禁用；
- 检查结束后 60 秒内点击时复用刚才结果；
- 60 秒后允许再次主动检查；
- 不改变后台现有的 12 小时轮询和 4/24 小时网络失败退避。

## 9. 错误处理

### 9.1 网络检查失败

后台自动检查网络失败继续保留上一次稳定状态，不显示错误提醒。

用户主动检查失败时，设置页根据本次返回状态中的 `lastNetworkErrorAt`、`lastCheckedAt` 和 `lastSuccessfulCheckAt` 判断本次检查未成功，并显示“暂时无法检查更新，请检查网络后重试”。

该失败不会：

- 清除已有 `available` 候选；
- 清除已下载文件；
- 覆盖 `downloaded`、`preparing` 或 `installing` 状态；
- 触发左下角网络错误提醒。

### 9.2 下载与校验失败

- 下载失败：显示失败原因和“重新下载”。
- SHA-256 缺失或不匹配：显示安全校验失败；重新检查 Release 元数据后才允许再次下载。
- 失败的 `.partial` 文件继续由现有清理逻辑处理。

### 9.3 安装失败

已校验的下载文件仍然存在时显示“重试安装”，并再次经过安装确认弹窗。文件不存在或无效时退回重新检查或下载流程。

### 9.4 左下角重试动作

现有点击动作按错误类型细分：

- 下载错误：调用 `downloadUpdate()`；
- 校验错误：重新检查候选与校验文件；
- 安装错误且下载文件有效：打开安装确认弹窗；
- 其他可恢复错误：重新检查更新。

这避免把未完成的下载误当成可安装文件。

## 10. 外部链接

“查看官方发布说明”使用候选版本已有的 `releaseUrl`，通过 `target="_blank"` 触发现有 Electron 导航守卫。主进程拒绝应用内新窗口，并使用系统浏览器打开 HTTP/HTTPS 外链。

不新增任意 URL 打开 IPC，也不放宽现有导航安全策略。

## 11. 测试策略

### 11.1 主进程

增加最小回归测试覆盖：

1. 自动检查发现新版后仍会触发一次静默下载。
2. 手动检查发现新版后停在 `available`，不会请求更新包。
3. `checking` 和 `downloading` 期间不会创建重复任务。
4. 手动网络失败保留之前的 `available` 或 `downloaded` 状态。
5. Release 标题和发布日期能进入并恢复共享状态。
6. 下载、校验、安装错误映射到正确重试动作。

### 11.2 前端

使用现有测试栈覆盖：

1. 浏览器模式不渲染软件更新卡片。
2. 八类状态映射到正确文案、按钮和禁用状态。
3. 60 秒内复用检查结果，超过 60 秒后允许重新请求。
4. 手动网络失败显示局部错误，但不改变稳定状态。
5. 设置页与左下角提醒对同一状态产生各自约定的显示行为。
6. 安装按钮继续先打开确认弹窗。

### 11.3 回归验证

- Desktop 单元测试与类型检查；
- Frontend 单元测试、类型检查和生产构建；
- 打包桌面应用中手动走通“最新版、发现新版、下载中、已下载、安装确认、失败重试”状态。

## 12. 验收标准

1. 桌面端设置页在正确位置显示软件更新卡片，浏览器模式隐藏。
2. 用户可主动检查正式版更新，并获得明确结果。
3. 手动检查发现新版后不会自动下载。
4. 用户可主动开始下载并看到共享进度。
5. 下载完成后可经过确认执行安装并重启。
6. 自动更新行为保持不变。
7. 自动与手动路径不会产生重复检查、重复下载或状态覆盖。
8. 网络、下载、校验和安装失败均按约定恢复，且不破坏已有可用文件或稳定状态。
9. 左下角提醒继续只承担必要提醒职责。
10. 不新增依赖、数据库迁移或预发布更新设置。
