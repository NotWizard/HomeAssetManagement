## 第一批：数据正确性（🔴 + 🟡）

### V2-1 🔴 FX 汇率"错日期"落库：非交易日抓到的最近交易日汇率被存成当天精确值

- **位置**：`backend/app/services/fx_service.py:305`（`_fetch_chinamoney`）、`:357`（`_fetch_frankfurter`）、`:213`（`_upsert_daily_rates`）
- **证据**：chinamoney 请求 `startDate=rate_date-14天, endDate=rate_date, pageSize=1`，返回窗口内最近一个交易日记录，但代码只取 `records[0].values`，从未读取记录自身日期；frankfurter `GET /v1/{date}` 周末返回前一工作日数据，代码不校验响应 `date`；`_upsert_daily_rates` 无条件以入参 `rate_date` + `is_estimated=False` 写入。
- **影响**：每日汇率任务在周末/节假日把周五汇率落库为当天"精确"汇率（每年约 115 天）；`resolve_rate_for_pair` 返回 `is_estimated=False`，UI 不提示估算，`revalue_all_snapshots` 将其当作历史真理源。
- **修复建议**：chinamoney 解析记录自带日期、frankfurter 校验响应 `date`，以实际汇率日期落库（或保留 `rate_date` 但置 `is_estimated=True`）。

### V2-2 🔴 基准币切换后 `daily_totals` 历史行不重建，与 snapshot payload 永久失同步

- **位置**：`backend/app/services/snapshot_service.py:275-319`（`revalue_all_snapshots` 只重写 `payload_json`）；`_upsert_daily_total`（:462）仅被 `create_daily_snapshot` 调用
- **证据**：`revalue_all_snapshots` 两个循环均只赋值 `row.payload_json`，全程无 `DailyTotal` 写入。
- **影响**：基准币切换后 `snapshot_daily.payload_json` 全部为新币口径，`daily_totals` 历史行仍是旧币口径，两量纲混杂，无自愈路径（当前前端无 `daily/summary` 消费方，属潜伏型）。
- **修复建议**：`revalue_all_snapshots` 内同步按新 totals 重建对应 `daily_totals` 行（与 payload 同事务）。

### V2-3 🟡 CSV 同一文件内重复业务键 → 重复持仓落库

- **位置**：`backend/app/services/import_service.py:341`（`_resolve_action`）、`:352`（`_apply_parsed_rows`）
- **证据**：action 在解析阶段基于预取的 `existing_holdings_by_key` 一次性定好；apply 阶段 insert 成功后不回写该字典。同一 CSV 两行同 `(type, name, member_id, category_l3_id)` 且库中不存在时，两行都判 insert 并各自成功（表无唯一约束）。
- **修复建议**：apply 循环内 insert 成功后回写 key，或解析阶段文件内去重并报错。

### V2-4 🟡 迁移导入前的 SQLite 备份在 WAL 模式下可能不是最新状态

- **位置**：`backend/app/services/migration_service.py:272-302`（`_create_sqlite_backup_before_import`）；`core/database.py:26`（`PRAGMA journal_mode=WAL`）
- **证据**：备份用 `shutil.copy2` 只复制主 `.db` 文件；WAL 模式下最近已提交数据可能还在 `app.db-wal` 未 checkpoint，复制途中写入会得到 torn copy。
- **修复建议**：改用 sqlite3 在线备份 API（`source.backup(target)`），或复制前强制 `PRAGMA wal_checkpoint(TRUNCATE)` 并连同 `-wal`/`-shm` 一起复制。

## 第二批：桌面更新链路（🔴 + 🟡）

### V2-5 🔴 更新器死锁：`checking`/`downloading` 瞬态被持久化，重启后永久卡死

- **位置**：`desktop/src/update-controller.ts:570/745/792`（瞬态落盘）、`:229-310`（`sanitizePersistedState` 不覆盖 checking/downloading）、`:551`（入口守卫直接 return）
- **影响**：下载/检查中途退出或崩溃 → `state.json` 残留瞬态 → 自动轮询、手动检查、重试全部静默 early-return，更新功能永久失效且无 UI 提示，只能手删 state.json。
- **修复建议**：sanitize 时 `checking`→idle、`downloading`→按 `downloadedFilePath` 是否存在回退 `downloaded`/`available`；或持久化时把瞬态映射为可恢复态。

### V2-6 🔴 更新下载写流缺 error 监听 + 异常路径不关流，可致主进程崩溃

- **位置**：`desktop/src/update-controller.ts:777-838`
- **证据**：`createWriteStream` 后循环内持续 `write`，error 监听直到 :822 循环结束后才挂；catch 分支 `rmSync(partialPath)` 时流未关闭；`write` 返回值被忽略无背压。
- **修复建议**：建流即挂 error 监听；catch 中先 `destroy()` 再 rm；循环按 `write` 返回值 + `drain` 做背压。

### V2-7 🟡 更新链路所有 fetch 均无超时

- **位置**：`desktop/src/update-controller.ts:379/399/441/754/770`
- **修复建议**：全部加 `AbortSignal.timeout(...)`（元数据 30s，下载按进度看门狗）。

### V2-8 🟡 `before-quit` 的 SIGKILL 兜底被 `.unref()` 架空

- **位置**：`desktop/src/backend-controller.ts:83-94`；`main.ts:47`（`BACKEND_KILL_GRACE_MS` 死常量）
- **证据**：unref 定时器不阻止进程退出，同步 before-quit handler 执行完即退出，4s 宽限期走不到，SIGKILL 永不发出 → 可能留僵尸 sidecar 持有同一 SQLite + 双份调度任务。
- **修复建议**：退出路径同步等待子进程 exit（超时后 SIGKILL），或停 backend 改为阻塞式 kill 流程；删除死常量。

### V2-9 🟡 发布流水线漂移：tag 版本与 package.json 版本无一致性校验；release 只构建 arm64

- **位置**：`.github/workflows/release.yml`（无断言）；`update-controller.ts:349`（从 tag 解析版本拼资产名）；`make-macos-release.mjs:52`（产物名取自 package.json）
- **影响**：发 tag 忘 bump 版本号 → 产物名与更新器期望不符 → 更新静默失效无报错；x64 用户永远收不到更新。
- **修复建议**：release.yml 加 tag↔package.json 版本一致性断言；x64 支持缺口在 README/文档中显式声明。
